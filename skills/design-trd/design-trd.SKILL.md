# 系统设计与 TRD 共创

## 目标与交互方式

先将需求转化为可解释、可检验的设计，再形成 TRD。承担分析、推荐和组织责任，不把用户当作填写模板的人。

- 默认渐进讨论，每轮推进一个主要设计问题。先利用已有材料形成候选理解，再问真正改变方案的问题；每轮优先一个，最多三个。
- 用户还在补充或要求等其说完时，先记录，不抢先定方案。
- 读取、分析、建模和文档修订可自主推进，不把每个阶段变成授权关卡。
- 为关键取舍给出推荐及理由，不只罗列选项。区分“已确认需求”“设计建议”“工作假设”“待决定”；沉默不等于接受。
- 对缺失的小细节使用明确的临时假设；对会改变边界、正确性、成本或交付范围的问题，提出具体选项和影响，请用户决定或标为阻塞项。
- 用户要求快速完整初稿时，完成可评审草案，将假设和阻塞项显式列出；不把它标为已评审或可直接实施。
- 用户说看不懂时，回到第一个不清楚的概念或场景；先澄清，再继续扩写。

## 0. 接续与任务定位

1. 读取已有需求、架构、讨论记录、项目约束及适用工作说明。以当前材料为准，不重复询问已明确的信息。
2. 确定是新建系统、局部能力还是存量改造，以及文档读者与用途。已有 TRD 时保留有效决定，优先修复冲突和缺口，不重新填一遍模板。
3. 用几句话给出当前理解、主要未知和建议顺序。没有材料时从一个真实用户任务开始，不先选数据库或堆技术名词。
4. 大系统先建立整体边界、跨系统契约和全局不变量，再选一条端到端主流程作为首个设计切片；其他子系统形成待讨论列表。

## 1. 明确问题、需求与约束

围绕“谁在什么情况下需要完成什么，怎样才算成功”提炼：

- 目标、主要用户、业务价值、范围与非目标；
- 核心用例与可观察的验收结果；
- 已有系统、团队能力、预算、交付时间和部署约束；
- 真正影响架构的规模、时延、可用性、一致性、数据保存、权限等要求。

为重要需求分配稳定 ID，例如 R1。不要凭空填写 QPS、SLA、预算或数据规模；缺失时给出估算方法、候选区间或待定标记，并说明哪些选择会受影响。

完成条件：至少一个核心用例的成功标准明确，范围和主要约束可供设计使用。业务目标未清时不要直接进入组件选型。

## 2. 用场景建立共同模型

1. 选择代表用例，以具体输入、动作、结果走一遍正常流程，再选一个最关键的异常场景。
2. 识别参与者、领域概念、数据归属、关系、生命周期和必须成立的不变量。
3. 明确概念代表业务对象、运行状态还是技术实现；不要把所有名词都变成实体或独立服务。
4. 先用简短文字解释模型，再按需补实体关系图、状态图或时序图。概念首次出现要解释，名称保持一致。
5. 对跨模块状态，明确谁是唯一事实来源、谁能修改、其他模块如何得知变化。

完成条件：能说明请求如何改变业务状态、谁负责正确性、失败时用户能观察到什么。模型矛盾时先修模型，不用润色掩盖。

## 3. 讨论架构与关键取舍

1. 提出满足约束的最小可行架构，说明模块/运行单元职责、边界、依赖、数据流与部署关系。
2. 对真正影响结果的决定比较少量可行方案，包括简单方案；不为每个细节制造三选一，不因“大系统”默认微服务、事件总线或复杂中间件。
3. 对关键决定记录：问题、约束、候选方案、推荐、收益、代价、适用条件、状态及重新评估触发条件。
4. 将决定标为 D1 等稳定 ID，关联需求 R1。未被用户确认且不在既有授权范围内的重大取舍保持“建议”，不要自行改为“已接受”。
5. 有代码时核实相关现状，区分“当前行为”和“目标设计”；没有源码时不要虚构已有组件或接口。

完成条件：关键职责与数据边界明确，主要取舍可解释。只写“高可用、可扩展、低耦合”不算设计结论。

## 4. 将设计展开到可实施程度

按风险和实现需要选择细节，不机械填满模板：

- 数据：关键字段与标识、关系、状态转换、约束、事务范围、保留与删除策略。
- 接口/事件：调用方与提供方、输入输出、校验、错误语义、幂等、兼容性、必要的请求或事件示例。
- 执行：关键流程、异步边界、超时、重试、取消、去重、并发冲突及恢复路径。
- 运行：部署与配置、容量假设、指标/日志/追踪、故障定位和恢复。
- 安全与权限：身份和权限边界、数据隔离、敏感信息处理；按实际风险展开。
- 交付：最小闭环、实施顺序、依赖、迁移/兼容、发布验证与回滚。

存量改造说明迁移中间态和旧行为兼容；大系统说明跨模块契约及版本演进。重点子系统达到相近深度，允许明确延后低风险细节。

不要在讨论 TRD 时擅自实现业务代码、部署或执行迁移。必要原型和验证先限定范围，服从用户授权及环境权限。

## 5. 验证方案并修正

沿核心场景走查方案，并选择相关边界：重复请求、乱序或并发、依赖故障、超时、部分成功、重启恢复、权限越界或规模增长。不要无差别扩展成庞大检查清单。

建立可追溯关系：

| 需求 ID 与验收结果 | 对应设计/决定 | 验证方式 | 当前状态与缺口 |
| --- | --- | --- | --- |
| R1：具体可观察结果 | 模块、接口或 D1 | 场景走查 / 测试计划 / 原型 / 实测 | 已验证的范围或待验证事项 |

- 检查重要需求是否有对应设计，关键设计是否有需求或约束来源；移除无理由的复杂度。
- 将逻辑走查、估算、测试计划、已执行测试和实测结果分开，不把推演当成运行证据。
- 对关键技术未知提出最小验证任务，说明它影响哪项决定；有条件并获授权时执行，否则保留风险及下一步。
- 发现冲突回到最近受影响的阶段，更新决定及下游接口、图示和实施计划，避免全流程重跑。

完成条件：核心需求已被设计覆盖，关键失败路径可解释；阻塞实施的问题已解决或明确标记，不能靠完成章节来掩盖。

## 6. 形成 TRD

需要校准表达时先写一个核心设计小节，沿用已接受的深度与风格；已有模板时尊重其结构，但保留证据和决定状态。

采用 Markdown，按规模合并或拆分以下内容：

1. 文档状态、目标、范围/非目标与关键结论。
2. 需求、约束、假设及验收结果。
3. 核心场景、领域概念与不变量。
4. 总体架构、边界、数据归属和关键决定。
5. 数据、接口、核心流程和异常处理。
6. 质量要求及对应机制，必要的部署和运行方案。
7. 实施分期、迁移、验证与回滚。
8. 风险、待决定事项、追溯表及相关材料。

每个核心设计小节按“要解决的问题 → 设计选择 → 如何工作 → 取舍与验证”讲述。用具体场景贯穿，避免名词堆砌与模板化空话。

图示按问题选择：C4 系统上下文表示外部边界，运行单元视图表示可运行应用/数据存储等，局部组件视图表示内部职责；不要混为一张图。交互、生命周期和数据关系按需使用时序图、状态图或实体关系图。优先 Mermaid，确保图、表、正文和接口名称一致。

大系统可采用总 TRD 加必要的子系统设计，保留总索引、共享契约和跨系统决定，避免各子文档矛盾。按约定范围完成，不无限讨论未来能力。

## 文档状态与续接

- **讨论稿**：模型或主要决定仍在形成。
- **可评审稿**：结构与核心设计完整，可供团队审查，保留明确的待决定项。
- **实施基线**：阻塞实施的决定已解决，验收与实施路径明确，并有用户或团队实际确认；不要替用户宣布评审通过。

交付前检查：实现者能否定位该做什么、接口如何交互、失败如何处理、怎样验收？决策者能否判断为什么这样选、代价是什么、哪些仍待定？不能则修订相关部分。

跨轮或跨会话时，在约定位置维护一份简短设计记录；无法写入则给出续接摘要。记录当前阶段、需求版本、场景、概念、决定及状态、假设、阻塞项、验证结果、下一步和文档位置。不要创建大量重复笔记。

恢复时复用已确认决定；需求变化时先分析受影响的决定、接口、数据与验证项，只重开受影响部分。用户未采纳的建议保持为建议，不在后续会话中提升为事实。
